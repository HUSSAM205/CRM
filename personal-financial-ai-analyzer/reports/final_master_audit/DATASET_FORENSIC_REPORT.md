## 3. Field semantics as enforced

| Field | Use | Enforcement |
|---|---|---|
| `transaction_id` | Deduplication and traceability only | Never a feature (L1/L7 test) |
| `account_id` | Grouping and splitting only | Never a feature; account-disjoint robustness panel |
| `transaction_type` | Fixed mapping in `configs/financial_rules.yaml`: outflows are debit, withdrawal, fee and transfer (transfers neutral); inflows are credit, deposit, interest and refund (refunds reduce their category) | `test_financial_rules.py`; ledger 49M/49M |
| `amount` | Positive magnitude → integer cents; \|x\| > 10¹² rejected | `test_validation.py` |
| `currency` | Always part of the aggregation key; never summed across currencies | `MixedCurrencyError` test |
| `merchant_category` | Expense grouping; anomaly feature | — |
| `balance_after` | **Excluded everywhere** (leakage, mixed currencies) | Feature guard plus grep |
| `transaction_timestamp` | Strict parsing; calendar features | Invalid → rejected with a reason |
| `status` | Only `completed` enters totals | Status tests |

## 4. Isolation of the public dataset and user uploads

* Training reads only `data/raw` and its derived tables.
* The app keeps uploads in session memory only. It never writes them to disk (`test_app_never_writes_uploads_to_disk`), never feeds them into training, and never sends them anywhere (0 network calls in `app/` and `src/`).
* Logs contain no transaction or account IDs (`reports/audit/static_security_scan.txt`).

## 6. Data engineering

* PyArrow and Polars, reading row groups.
* 50 account partitions, each processed in a child process under a 4 GB hard limit and a 3 GB soft target.
* Checkpoints with resume.
* Partitioned intermediate tables in `data/processed/`.
* No full pandas load anywhere.
